# design-check — 코딩 전 확인 절차

목적: 기존 경로를 모른 채 새 경로를 만드는 사고를 막고, 추론으로 설계를 채우지 않는다.

## 순서

1. **설계 문서 읽기** — `Assets/Docs/` 에서 해당 문서·절을 찾는다 (서바이벌 = `SurvivalDesign.md`, 네트워크 = `NetworkDesign.md`, 응원 = `CheerSystemDesign.md`, 스테이지별 문서 등). "문서에 없음" ≠ "미정". 채팅·메모리에서 이미 정한 게 있을 수 있으니 미정으로 단정하지 않는다.
2. **도메인 주인 읽기** — `Assets/Docs/GameArchitectureBoundaries.md` 에서 이 기능이 어느 도메인 소속인지, 바꾸려는 상태의 주인이 누군지 본다.
3. **전체 grep** — 기능 키워드(예: `Revive`, `Round`, `Arrival`, `Damage`)로 `Assets/` 전체를 검색해 관련 스크립트를 **전부** 나열한다. 하나만 읽고 끝내지 않는다. 각 스크립트가 뭘 하는지 한 줄씩 적는다. 이 저장소는 신규보다 재사용을 강하게 선호한다.
4. **선택** — 재사용 / 확장 / 신규 중 하나를 고르고 이유를 적는다. 신규는 "기존 것으로는 안 되는 이유"가 있어야 한다. 서바이벌이면 `SurvivalDesign.md` §4.3 기준으로 기존 스토리 코드에 손대는 양·다시 테스트할 범위를 같이 적는다.
5. **미정 항목 나열** — 구현에 필요한데 문서·채팅 어디에도 없는 값·규칙을 목록으로 뽑는다(발동 조건 / 대상 선정 / 연출 / 인원별 값 / Host·클라 누가 판정). 추론으로 채우지 않는다.
6. **보고하고 멈춘다** — 아래 형식으로 사용자에게 보고하고 승인을 기다린다. 승인 단어는 CLAUDE.md 기준.
7. **승인 뒤** — 코드 작성 → 도메인 주인이 바뀌었으면 GameArchitectureBoundaries.md 갱신 → 결정된 미정 항목을 설계 문서에 적음 → 에디터 체크리스트 제공 → 커밋 권유.

```
기존 스토리 코드 영향: (손대는 양 / 다시 테스트할 범위, 없으면 "없음")

미정 (답 필요): 1. ... 2. ...

```
