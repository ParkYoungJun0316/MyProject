## 0. 한 줄 요약

10×10 격자의 **칸과 칸 사이 모든 경계가 색 문**이고 **시작은 전부 닫힘**이다.
1층의 **러너 1명**은 혼자서는 한 칸도 못 움직이고, **2층에서 내려다보는 안내자들이 색 패드를 밟아
문을 열어줘야만** 앞으로 간다. 한 번에 한 색만 열리므로 start→goal은 **색을 최소 12번 갈아타는 여정**이다.
체이서는 **문을 무시하고 직선으로** 쫓아오므로, 위험한 순간은 막다른 길이 아니라 **문 앞에서 기다리는 시간**이다.

## 1. 확정 결정

### 1.1 구조 — 한 판. 맵도 한 장 (2026-09-20)

> **T5는 T.Stage4와 같은 경로만 탄다.** 씬 로드 → 시드로 러너 1명 + 색 순열 → 시작 → 클리어/실패.
> 스테이지 안에서 상태가 넘어가는 구간(라운드 전환)이 **없다.**

**저장소에서 허용하는 스테이지 형태는 둘뿐이다 (2026-09-19 사용자 확정):**

| 형태 | 예 |
|---|---|
| **(a) 씬 = 스테이지 1개** | T.Stage4, T.Stage5 |
| **(b) `PhaseManager` + phase마다 StageManager** | T.Boss 류 |

| 항목 | 결정 |
|---|---|
| 판 수 | **1** |
| 맵 | **1장.** 7장 추첨 폐기 — 지형이 고정돼도 §1.12의 두 축이 매판 판을 바꾼다 |
| 러너 | **1명.** 솔로 = 본인 |
| 러너 교대 | **없다.** 실패 시 로테이션으로 자연 교대(§1.10) |
| 리로드 시 | 새 시드로 **러너 재추첨 + 고유색 순열 재추첨** |
| 제한 시간 | **110초** (실측 밴드 **100~120**, §1.8) |
| 실패 | **러너 사망 · 안내자 사망 · 시간 초과** |
| 클리어 | **러너가 1층 Goal + 안내자 전원이 2층 Goal** (§1.8) |
| 부활 | **없다 — 누가 죽든 즉시 실패**(§1.8). SSOT는 `ReviveSystemDesign.md` §7.1 |

### 1.2 시작 시나리오

**텔레포트를 쓰지 않는다.** 플레이어는 스폰한 자리에서 물리적으로 2층에 올라간다.

| # | 시점 | 일어나는 일 | 주체 |
|---|---|---|---|
| 0 | 씬 로드 | 색별 고정 스폰 `(0,0,5)/(5,0,0)/(0,0,-5)/(-5,0,0)`. 커튼 덮인 채 | `PlayerSpawnManager` |
| 1 | `OnPlayersReady` | 시드로 **러너 1명 + 고유색 순열** 확정 → 색 매핑 적용 → **러너 발판만 끄기** → 게이트 `t5.map` 해제 → 커튼 걷힘 | 디렉터 |
| 2 | 즉시 | 각자 자기 `ColoredStartZone` 안 → **3초 카운트다운** | `StageStartGate` |
| 3 | 카운트다운 완료 | `StartStage()` + **발판 활성화**(러너 것 제외) → 안내자가 투명 통로를 타고 2층으로 발사 | `OnCountdownComplete` |
| 4 | **2층 트리거 발동** | **발판 끄기 + barrier 전부 해제** (같은 스위치) | 디렉터 |
| 5 | 러너가 시작 존 이탈 | **체이서 4마리 스폰** | 이탈 트리거 |
| 6 | — | 러너 1층 Goal + 안내자 2층 Goal → 클리어 / 110초 → 실패 | `T5RunnerObjective` |

**왜 이 순서인가 — 세 가지가 이 순서에 걸려 있다:**

1. **색 확정이 `OnPlayersReady`인 이유.** 사망 리로드 때 새 시드가 Host→ClientRpc로 오는데
   `Start()`보다 먼저 도착한다는 보장이 없다. **문 색이 곧 이번 판의 지형**이므로, 커튼이 걷히기 전에
   매핑이 끝나 있어야 한다. 커튼이 덮고 있으므로 플레이어에게는 **"눈 떠보니 이 배색"** 으로 보인다.
   → 게이트 문자열 **`"t5.map"`은 그대로 쓴다**(맵 선택이 사라져도 "이번 판 확정 완료"라는 뜻은 같다).
2. **barrier를 4단계까지 유지하는 이유.** 카운트다운 직후에 내리면 러너가 **옆 칸 발판을 밟아**
   2층으로 올라갈 수 있다. `ContactKnockback`에는 대상을 고르는 기능이 없어서, 발판이 켜져 있는
   동안 barrier로 막는 것이 유일한 구조적 차단이다.
3. **2층 트리거를 3단계에 미리 켜두지 않는 이유.** `ContactKnockback`은 **속도 방향을 보지 않는다.**
   미리 켜면 발사돼 올라가던 사람이 통과하며 **한 번 더 가속**돼 난간(6m)을 넘는다.

> **러너가 시작 존에서 안 나가면 체이서가 안 나온다 — 그대로 둔다.**
> 110초 타임아웃이 실패로 끝내므로 교착이 아니다.

**수직 발사 수치:** `ContactKnockback.VerticalUp`. Player mass = 1이라 force가 곧 초기 속도이고
**정점 높이 ≈ force² / 19.62** — 2층 y≈25면 **force ≈ 22.1**이 정점에서 속도 0인 값이다.
모자라면 시작 홀에 도로 떨어지고 **발판을 다시 밟아 재발사**되므로(`knockbackInterval` 0.25초)
실패가 자기 복구된다. 넘치면 난간을 넘는다 — 실측으로 잡을 것.

### 1.3 2층에서 1층으로 못 내려간다

2층 바닥에 **발사 구멍이 하나** 있다(원점 ±6, 12×12 — 스폰 4자리가 ±5 안이므로 넷을 다 덮는다).
그 구멍은 곧 내려가는 길이기도 하다.

| 안 | 내용 | 상태 |
|---|---|---|
| **가** | 구멍에 **트리거 + `VerticalUp` 약하게** — 내려가려 하면 다시 올라감 | **채택(테스트 선행).** `ContactKnockback`은 `Is Trigger = true`를 명시적으로 지원하므로 **코드 0** |
| 나 | 전원 2층 도달 후 뚜껑 콜라이더 켜기 | 가가 실패하면 |
| 다 | 그냥 열어둠 | ✗ 안내자가 1층으로 걸어나가 2층 Goal에 못 감 |

### 1.4 문 — **격자의 모든 변이 문이다** (2026-09-20 전면 교체)

> **구 설계는 "벽으로 만든 미로 위에 문 15개"였다. 그게 쉬웠던 이유는 단순하다 —
> 러너가 문 앞까지는 혼자 갈 수 있었기 때문이다.** 경로 위에 문을 늘려도, 벽 몇 개를 문으로
> 바꿔도 그 성질은 안 변한다. 그래서 **벽을 전부 없애고 전부 문으로 바꾼다.**

| 항목 | 결정 |
|---|---|
| 격자 | **10×10칸** |
| 통로 폭 | **10** (구 8에서 확대 — 한 번 열렸을 때 달리는 거리를 늘리려고) |
| 문 두께 | **2** |
| 피치 | **12** = 통로 10 + 문 두께 2 → 전체 **120×120** |
| 문 개수 | **180개** = 2 × 10 × 9 (내부 경계 전부) |
| 문 규격 | 폭 10 × 높이 15 × 두께 2 · `openMode = SlideUp` · `latchOnOpen = false` · `requiredPads` 비움 |
| 외곽 | **진짜 벽**(문 아님). 단 **시작칸 (0,0)의 남·서 외벽만 뚫는다**(시작 홀과 연결) |
| 색 | **고유 4색(Blue/Purple/Green/Yellow) + 흑 + 백 = 6** — 색당 평균 30개 |
| 시작 상태 | **전부 닫힘** |
| 규칙 | 패드 1개를 밟으면 **그 색 문만 Open, 나머지 전부 Close**(배타). 흑·백도 같은 규칙의 한 색 |
| **점유 = 마지막으로 밟은 패드** | **서 있는 것으로는 점유를 되찾지 못한다.** 발동은 `OnTriggerEnter` 하나뿐 |
| 색 매핑 | **러너 색 → `Common`(누구나 엶) · 이번 판에 없는 색 → 벽**(영영 안 열림). 2026-09-20 확정 |
| NavMeshObstacle | **붙이지 않는다** — 체이서가 문을 관통하므로(§1.7) |

**왜 120×120인가 (2026-09-20 사용자 확정, A/B 비교 후 B 채택):**

| | A안: 통로 10 · 문 두께 1 | **B안(채택): 통로 10 · 문 두께 2** |
|---|---|---|
| 피치 | 11 → 전체 110×110 | **12 → 전체 120×120** |
| 칸 중심 | 5.5, 16.5 … **비정수** | **6, 18, … 114 정수** |
| 2층·난간·발사통 | 110으로 **전부 재제작** | **이미 만들어 둔 120 그대로 재사용** |

1. **"몇 걸음 못 가고 선다"를 결정하는 건 통로 폭이 아니라 피치**다. 문 두께 2는 통로 길이에
   그대로 보태진다 — 폭만 넓히고 두께를 깎으면 넓힌 만큼 도로 까먹는다.
2. 120이 유지되면 `T5_Common`(Floor2F·Rails2F·LaunchShaft·DescentBlocker)과 시작 홀이 **그대로 산다.**
   버리는 것은 미로 벽 448개뿐이다.
3. 칸 중심이 정수라 덤프·검증 스크립트가 그대로 돌아간다.

**좌표계**

| 것 | 값 |
|---|---|
| 범위 | **0 ~ 120** (x, z). 칸 피치 **12** |
| 격자선 (문이 서는 줄) | 0, 12, 24, … , 120 |
| 칸 중심 | 6, 18, 30, … , 114 |
| start 칸 중심 | **(6, 6)** — 좌하단 |
| goal 칸 중심 | **(114, 114)** — 우상단 |
| 문 자리 | **(격자선, 칸 중심)** 또는 **(칸 중심, 격자선)** — 예: `(12, 18)` |
| 체이서 스폰 4점 | S(54, 6) · W(6, 54) · N(54, 114) · E(114, 54) |
| 2층 바닥 / 난간 | −6 ~ 120 (시작 홀 쪽으로 6m 여유) |

> **⚠️ 전환 1회에 움직이는 문은 60개다 — 180개가 아니다.**
> 배타 게이트라 **열려 있던 색 30개가 닫히고 새 색 30개가 열린다.** 나머지 120개는 이미 닫혀 있어
> `Close()`가 무동작이다. 연출·물리 부하를 여기 기준으로 볼 것.

> **⚠️ 문턱에 서 있으면 러너가 튕긴다.** `DoorController`의 닫힘 넉백은 **`Player`에만** 걸린다
> (`TryKnockback`이 `Player` 컴포넌트를 요구 — 체이서는 영향 없음). 전환 순간 러너가 닫히는 문
> 안에 있으면 밀려난다. **이건 버그가 아니라 "문턱에서 어물거리지 마라"는 사양으로 둔다.**

> **⚠️ "없는 색 → Common"을 그대로 쓰면 2인에서 스테이지가 사라진다 (2026-09-20 실측 → 규칙 분리).**
> 문이 15개일 때는 합쳐져 봐야 8개짜리 이야기였는데, **180개가 되니 규모가 달라진다.**
>
> | 인원 | Common 묶음 | 그 묶음의 최대 연결 성분 | 최소 전환 |
> |---|---|---|---|
> | 4인 | 30문 (러너 색만) | 14칸 | 12 |
> | 3인 | 59문 | 13칸 | **7** |
> | 2인 | **89문 = 문의 절반** | **24칸** | **5** |
>
> 2인이면 패드 하나로 문 절반이 동시에 열려 러너가 거의 걸어서 골인한다. 그래서 규칙을 쪼갠다 —
> **러너 색은 Common(열림), 없는 색은 벽(안 열림).** 이러면 인원이 줄수록 격자가 **촘촘해진다**
> (실측: 2인 13~14전환 > 4인 12전환). 연결성은 §1.6의 **흑 ∪ 백 조건**이 전 인원에서 보장한다.
> 이건 이미 확정한 솔로 규칙("고유색은 전부 벽 — 열어줄 사람이 없으니")을 2·3인으로 연장한 것이다.

> **⚠️ 미로 지표가 전부 무의미해졌다.** 막다른 길·루프·"정답 경로 53칸" 같은 구 기준은
> 벽이 사라지면서 같이 사라진다. 난이도를 만드는 축은 이제 **지형이 아니라 색 배치**다(§3.3).

### 1.5 패드 — 2층을 9구간으로 나누고 구간마다 전 색을 둔다 (2026-09-20 신규)

**구 설계는 "맵당 색당 1개 = 6개를 2층 곳곳에 흩어 배치"였다.** 그러면 안내자가 패드를 찾아
뛰어다니는 동안 러너가 문 앞에 서 있는다. **전환이 12회 이상인 새 구조에서는 치명적이다.**

**2층을 3×3 = 9구간(각 40×40m)으로 나누고, 구간마다 전 색 패드를 한 묶음씩 둔다.**
안내자는 **러너를 따라 위에서 이동하며 그 자리에서 누른다.**

```
 z
120 +---------+---------+---------+
    |    7    |    8    |    9    |   구간 중심 = 패드 클러스터 위치
    |(20,100) |(60,100) |(100,100)|
 80 +---------+---------+---------+   넘버패드 배치와 같다
    |    4    |    5    |    6    |   (1 = 좌하단 = 시작칸 쪽,
    | (20,60) | (60,60) |(100,60) |    9 = 우상단 = Goal 쪽)
 40 +---------+---------+---------+
    |    1    |    2    |    3    |
    | (20,20) | (60,20) |(100,20) |
  0 +---------+---------+---------+
    0        40        80       120  x
```

| 항목 | 결정 |
|---|---|
| 구간 | **3×3 = 9** · 각 40×40m |
| 구간당 패드 | **6개 authored** = 고유 4색 + 흑 + 백 |
| 배치 | 구간 중심에 **반경 4m 링**으로 6개. 안내자가 가운데 서서 밟는다 (간격 ≈ 4.2m — `OnTriggerEnter` 오발 방지) |
| 총 패드 | **54개** (9 × 6) |
| 패드 권한 | 고유색 패드 = **그 색 플레이어만** / 흑·백·Common = 누구나 |
| 없는 색 패드 | **숨긴다** — 그 색 문은 벽이라 열 대상이 없다(§1.4) |
| Common 패드 | 구간당 **정확히 1개** — Common으로 떨어지는 것은 러너 색 하나뿐이라 자동으로 1개다 |
| 구간 이동 | 구간 중심 간 40m ≈ **4초** — 전환 1회당 예산과 맞물린다 |

**인원별로 실제로 보이는 패드:**

| 인원 | 구간에 보이는 패드 |
|---|---|
| 4인 | 고유 3 + Common + 흑 + 백 = **6** |
| 3인 | 고유 2 + Common + 흑 + 백 = **5** |
| 2인 | 고유 1 + Common + 흑 + 백 = **4** |
| 솔로 | **전부 숨김**(§1.6) |

> **⚠️ 이 변경이 협동을 죽이지 않는 이유.** 고유색 패드는 **그 색 플레이어만 밟을 수 있다.**
> 구간마다 전 색이 있어도 **한 명이 다 처리할 수 없고**, 안내자 전원이 러너를 따라 움직여야 한다.
> 역할이 **위치가 아니라 색으로** 갈린다. 대신 생성기가 **의도 경로에 고유 4색을 각각 2회 이상**
> 넣어야 한다(§3.3-7) — 안 그러면 한 번도 안 누르는 안내자가 생긴다.

> **규칙 변경(2026-09-20 승인):** 구 규칙 **"2층 Common 패드는 1개만"** 은 **"구간당 1개"** 로 바뀐다.
> 그리고 §1.4의 벽 규칙 덕분에 **중복 제거 코드가 필요 없다** — Common으로 떨어지는 색이
> 러너 색 하나뿐이라 구간마다 저절로 1개다. `SceneReadyAndColorMapping.md` §B 갱신 대상(§7).

### 1.6 솔로 — 흑·백을 동시에 열어 고정 미로로 만든다 (2026-09-20 확정)

| 항목 | 솔로 규칙 |
|---|---|
| 고유색 문 + Common 문 | **전부 닫힘 고정** — 열어줄 사람이 없다 |
| 흑 문 + 백 문 | **동시에 Open 고정** |
| 2층 패드 | **전부 숨김** |
| 결과 | 솔로는 **"흑·백 문만 통로인 고정 미로"** 를 러너가 혼자 달리는 스테이지가 된다 |

> **구 규칙("솔로는 문 전부 Open")은 폐기한다.** 모든 경계가 문인 구조에서 전부 열면
> **벽이 하나도 없는 120×120 빈 들판**이 되어 대각선으로 18칸 달리면 끝난다.

**생성기 합격 조건은 이 한 줄로 요약된다 — "흑 ∪ 백 부분그래프가 start→goal을 연결할 것."**
그리고 **이 조건 하나가 1~4인 전부를 덮는다:**

- 솔로는 흑·백이 **동시에** 열리므로 통로 = (흑 ∪ 백).
- 다인승은 한 번에 한 색이지만 **흑↔백을 무한히 번갈아** 밟을 수 있으므로, 시간축을 펴면
  도달 가능 범위가 역시 **(흑 ∪ 백)**.
- 즉 **두 경우의 도달 가능성이 동일하다.** 어떤 인원에서도 "흑백만으로는 못 간다"가 나오지 않는다.

> **⚠️ 그래서 흑백 경로는 일부러 길게 뽑는다(§3.3-6).** 흑백만으로 항상 클리어가 되면 4인에서도
> 흑·백만 번갈아 밟는 것이 정답이 되고, 고유색을 든 안내자 셋이 논다 — T5를 갈아엎는 이유였던
> 문제가 그대로 재발한다. **솔로는 전환 비용이 0이라 길어도 그냥 달리면 되고, 다인승은 한 칸마다
> 전환 비용이 붙어 흑백 고집이 시간 초과로 벌 받는다.** 같은 지형이 인원에 따라 다른 난이도가 된다.

### 1.7 체이서 — 문을 관통한다 (2026-09-20 변경)

| 항목 | 결정 | 구안 |
|---|---|---|
| 수 | **4마리 고정** (인원 무관, 솔로도 4) | 동일 |
| 스폰 위치 | **동서남북 4점 고정**, 씬 루트 (§1.4 좌표) | 맵마다 16점 |
| 스폰 시점 | **러너가 시작 존을 벗어날 때** | 동일 |
| **문** | **관통한다.** `NavMeshObstacle` 없음 + 물리 레이어로 문과 비충돌 | 닫힌 문이 막음(carve) |
| **속도** | **4 m/s** (러너 10) — 실측 조정 | 8 m/s |
| 데미지 | **2** (러너 `maxHeart` 5 → **3방 사망**) | 동일 |
| 피격 후 | 소멸(Host Despawn) | 동일 |
| 리스폰 | **없다** | 동일 |
| 타겟 | 러너만. 러너가 죽거나 은신이면 정지 | 동일 |

**왜 관통인가 / 왜 속도를 반으로 깎는가:**

문이 안 막으면 체이서는 **직선**으로 온다. 반면 러너는 지그재그로 돌고 **문 앞에서 선다.**
경로 27칸 = 324m를 대기 포함 60초에 간다면, start(6,6)→goal(114,114) 직선거리 **153m** 기준
러너의 **실효 접근 속도는 약 2.5 m/s**다. 여기에 직선 8 m/s를 붙이면 4마리가 러너에게 눌러앉아
**즉사 스테이지**가 된다. 4 m/s에서 시작해 실측으로 잡는다.

> **이 변경의 진짜 소득은 속도가 아니다.**
> **위험한 순간이 "막다른 길"에서 "문 앞에서 기다리는 시간"으로 옮겨간다.**
> 안내자가 늦으면 러너가 맞는다 — 비대칭을 협동으로 묶는 장치가 패드 배타 규칙 하나뿐이었는데,
> **안내 속도가 곧 러너의 생존**이 되면서 훨씬 강한 장치가 생긴다.

> **⚠️ 체이서는 소모품이다.** 리스폰이 없고 때리면 소멸하므로 **4마리 = 러너를 때릴 기회 4번**이다.
> 3방에 죽으므로(5→3→1→0) 2방까지는 버틴다. 4마리가 다 소진되면 남은 시간은 무위험 구간이 되고
> 압박은 시계만 남는다 — **의도된 곡선**이다.

**덤으로 따라오는 정리:**
- 문에 `NavMeshObstacle`이 없으므로 **전환마다 carve 재계산이 사라진다.** NavMesh는 **빈 사각형
  바닥 1회 베이크**로 끝이다(구 문서의 "베이크 시 Doors 비활성화" 주의도 불필요).
- **체이서 스폰칸의 `degree ≥ 2` 조건이 사라진다** — 어느 칸에 놔도 갇히지 않는다.
- 문 닫힘 넉백은 `Player` 전용이라 체이서에는 안 걸린다(코드 확인 완료).
- **남는 작업:** 체이서 콜라이더가 문짝을 물리적으로 통과하도록 **레이어 충돌 매트릭스**(에디터, §5).

### 1.8 목표 / 실패 — T5 전용 Objective 하나

> **`SurviveTimeObjective`를 쓰면 안 된다.** 그건 **시간을 채우면 `Complete()`** 다 —
> T5는 시간 초과가 **실패**다.

> **`ReachZoneObjective`도 그대로는 안 된다.** 완료 조건이
> `_reachedPlayers.Count >= GameSession.GetActiveColors().Count` — **존 하나가 전원을 요구**한다.
> 1층 Goal과 2층 Goal로 나누면 양쪽 다 영원히 미완이다.

| | 내용 |
|---|---|
| 클리어 | **러너가 1층 Goal 존 + 안내자 전원이 2층 Goal 존** 안에 있을 때 `Complete()` |
| 실패 | **110초** 경과 → `Fail()` → `StageNetworkState` 직접 실패 통보 |
| 플레이어 사망 | **러너·안내자 구분 없이 누가 죽든 이 클래스가 직접 구독해 `Fail()`** |
| 판정 | Host 레인(`ReachZoneObjective`와 동일 이유 — Client가 `Complete()`를 부르면 §11A 위반) |
| UI | **시간만 표시.** 진행률 표기 없음 |

**제한 시간이 90 → 110이 된 이유 (2026-09-20 사용자 확정):**

전환 12회 구조의 시간 산수(경로 27칸 · 피치 12 기준):

| | 주행 | 전환 대기 | 합 |
|---|---|---|---|
| 최적 12회 · 안내자가 미리 눌러줌(2초) | 32초 | 24초 | **56초** |
| 최적 12회 · 반응 지연(4초) | 32초 | 48초 | **80초** |
| 실전 16회(= 최적 12의 현실값) · 3초 | 32초 | 48초 | **80초** |

90초면 최적 플레이 말고는 거의 다 실패한다. **시간이 늘어도 2층이 계속 할 일이 있으므로
지루해지지 않는다**는 판단으로 **110초**를 기본값으로 잡고, 실측 밴드는 **100~120**이다.
(`T5RunnerObjective.timeLimit`의 현재 코드 값이 `120f`이므로, 120으로 확정하면 코드 수정이 0건이다.)

**부활을 안 주는 이유:**

1. **실패가 곧 러너 교대 기회다.** 실패 → 리로드 → 러너 재추첨(§1.10). 부활을 넣으면 같은 사람이
   계속 러너가 된다.
2. **형태가 맞는다.** `SequenceRingObjective`·`ColorTileChallenge`가 전부 "실수 1회 = 판 다시"다.
3. **부활 지점 override 훅이 불필요해진다.** 2층 안내자 옆에 부활하면 러너가 2층에 갇히고
   §1.3 때문에 내려올 수 없어 타임아웃까지 교착이다.

### 1.9 2층 압박 — 기존 함정으로

**문제:** 안내자는 위험이 0이다. 러너가 죽으면 아무 잘못 없는 셋이 같이 실패한다.

**채택 — 기존 `SpikeTrap`/`ContactDamage`를 2층에 배치**(사용자 작업). 이미 있는 비용만 쓴다.
**구간과 구간 사이에 놓으면** "러너를 따라 구간을 옮기는 것 자체가 위험"이 되어 §1.5와 맞물린다.
2층 Goal 존은 안전구역으로 둔다.

**폐기한 안 — 2층 체이서 1마리:** ① §2가 "2층에 렌더 메시를 붙이지 말 것"으로 NavMesh 미베이크를
구조적 보장으로 삼는데 그걸 깨야 한다 ② `Stage5ChaserAI`는 러너 clientId만 타겟한다
③ 2인이면 안내자 1명이 도망치면서 패드를 다 밟아야 해 인원별 격차가 커진다.

> ⚠️ **이게 안내자 사망을 가능하게 만든다 → 그래서 T5는 "누가 죽든 즉시 실패"다**(§1.8).

## 2. 씬 구성

맵이 1장이 되면서 **"맵마다 7벌"이 전부 사라진다.**

| 씬 루트 / `T5_Common` (이미 있음 — 그대로 둔다) | `T5_Maze` (재제작) |
|---|---|
| 시작 홀 · `StageStartGate` + `ColoredStartZone` 4 · barrier · 발판 4 · 투명 통로 | **`Floor1F`** ⚠️ |
| `Floor2F` · `Rails2F` · 2층 발사 구멍 트리거(`DescentBlocker`) | **`Doors`** (6색 그룹, 합계 **180**) |

| 체이서 스폰 4점 · 러너 시작 존 이탈 트리거 | **`Pads2F`** (9구간 × 6 = **54**, 2층) |

> `Floor2F`는 `BoxCollider`만 있고 `MeshRenderer`가 없는데 Surface가 **Render Meshes** 기준이라
> 자동으로 빠진다. **2층에 렌더 메시를 붙이지 말 것.**

### 3.0 도구

`Tools/T5MazeGen/`(Unity 밖, 빌드 비포함). **미로 생성기는 역할이 끝났다.**

| 파일 | 처리 |
|---|---|
| **`t5doors.py`** (신규) | 180개 문의 **색 배치**를 뽑는다 → `t5doors.json` |
| **`t5doorsemit.py`** (신규) | `t5doors.json` → 에디터 빌더가 읽는 평문 (`t5buildemit.py`와 같은 형태) |
| `t5gen.py` | **지우지 않는다.** 그 안의 **`min_switches()`가 §3.3 검증기 본체**다 |
| `t5maze.py` · `t5buildemit.py` · `t5maze.json` · `t5build.txt` · `t5maps.json` · `t5layout.txt` · `t5emit.py` · `t5verify.py` | **폐기 대상** — 벽 미로 전용. 사용자 확인 후 삭제 |

### 3.1 생성 절차 (`t5doors.py` — 구현 완료 2026-09-20)

1. **의도 경로**(27 또는 29칸)와 **흑백 안전망 경로**(41~45칸)를 **변이 안 겹치게** 깐다.
2. 의도 경로를 **14~16구간**으로 자르고 색을 배정 — 연속 구간은 다른 색, **고유 4색 각각 2회 이상**.
3. 흑백 경로는 **흑↔백을 1~2변마다 뒤집는다** — 짧게 끊어야 "흑백만 쓰면 비싸다"가 성립한다.
4. 남은 변(약 110개)을 **같은 색이 이어지지 않게**(매칭) 채운다.
5. **지름길 보정** — 하한 미달이면 제일 싼 길의 색 사슬을 끊는다(§3.2).
6. **오답 가지**를 심고, 하나 심을 때마다 하한을 다시 본다 (깨지면 그 가지만 롤백).
7. `t5gen.py`의 `min_switches()`로 인원별 전수 검증(§3.3). 떨어지면 다음 시드.

> **⚠️ 경로 칸 수는 홀수만 가능하다.** 격자가 이분그래프라 (0,0)→(9,9) 경로는 언제나 홀수 칸이다.
> 문서 초안의 "26~30칸"에서 실제로 만들 수 있는 값은 **27과 29**뿐이다.

### 3.2 왜 뽑기가 아니라 보정인가 (2026-09-20 실측)

**격자 기하가 하한을 정한다.** (0,0)→(9,9)는 최소 18수이고, 한 색으로 L칸을 달릴 수 있으면
전환은 대략 18/L이다. 2칸짜리 색 사슬이 깔려 있으면 **무엇을 그리든 9~10전환짜리 길이 생기고,
시드를 몇천 개 뽑아도 12가 안 나온다.** 그래서 뽑지 말고 **고친다** — 제일 싼 길을 복원해
그 길이 쓰는 색 사슬을 하나씩 끊는다(`repair()`).

끊는 방법은 변의 종류마다 다르다:

| 변 | 끊는 법 |
|---|---|
| 일반 변 | 이웃이 안 쓰는 색으로 바꾼다 |
| **흑백 경로 변** | **흑↔백으로 뒤집는다** — 색은 바뀌어도 흑 ∪ 백 집합은 그대로라 솔로 연결성(§1.6)이 안 깨진다 |
| 의도 경로 변 | 건드리지 않는다 (구간 구조가 곧 설계다) |

> **⚠️ 보정이 올릴 수 있는 천장은 구간 수 S다.** 의도 경로 자체가 언제나 S짜리 길이라
> 최소 전환은 S를 넘을 수 없다. 그래서 하한 12를 얻으려면 구간을 **14~16**으로 잡는다.

**한 번 열면 달리는 거리:** 경로 29칸 / 16구간이면 한 번 열릴 때 약 1.8칸(22m, 2.2초)이다.

### 3.3 합격 기준 — 전부 자동 검증 (구현값)

| # | 기준 | 값 | seed 7036 실측 |
|---|---|---|---|
| 1 | **최소 색 전환 (4인)** | **12 이상** (상한 없음) | **12** |
| 2 | 최소 색 전환 (3인, 없는 색 1개가 벽) | 10 이상 | 12~13 |
| 3 | 최소 색 전환 (2인, 없는 색 2개가 벽) | 8 이상 | 13~14 |
| 4 | **솔로 = 흑 ∪ 백 연결성** | 도달 가능 + 최단 **25~45칸** | 41칸 = **49초 주행** |
| 5 | **흑백만 고집할 때의 전환** | **20 이상** | **27** |
| 6 | 고유 4색이 의도 경로에 나오는 횟수 | 각각 2회 이상 | 충족 |
| 7 | **오답 가지** | **4칸 이상 × 6개** | 6개 |
| 8 | 색당 문 개수 | 18~45 | 25~37 |

**4·5번이 §1.6의 두 얼굴이다.** 4번은 "흑백만으로도 갈 수는 있다"(솔로 성립 + 다인승 안전망),
5번은 "그런데 비싸다"(4인 12전환 vs 흑백만 27전환)를 보장한다. 둘이 같이 있어야
"인원이 적으면 느리지만 막히지는 않는다"가 성립한다.

**검증기:** `t5gen.py`의 `min_switches()` — 상태 = **(칸, 열린 색)**, 색 전환 1회 = 비용 1,
이동 = 비용 0. **벽은 open_edges에서 빼서 표현한다**(`passable()`) — 검증기를 새로 만들지 않는다.

> **⚠️ 벽 규칙 덕분에 인원이 줄수록 전환이 늘어난다.** 구 규칙(없는 색 → Common)에서는
> 2인이 5전환이었는데(§1.4 ⚠️), 벽 규칙에서는 **13~14전환**이다. 대신 2인은 안내자가 1명이라
> 패드 왕복이 길다 — 난이도는 그쪽에서 조절된다.

> **⚠️ 12는 "최적값"이다.** 안내자가 순서를 틀리고 러너가 오답 가지에 들어가므로
> **실전 체감은 15~18회**다. 110초는 그 값을 기준으로 잡은 것이다(§1.8).

> **⚠️ 시드 색 순열은 전환 수를 바꾸지 않는다.** 고유 4색끼리의 교환은 라벨 교체라
> 결과가 불변이다 — 순열마다 재검증할 필요가 없다(§1.12).

**오답 가지 깊이가 6 → 4로 내려간 이유 (2026-09-20 실측).**
가지는 **지름길이 되면 안 되는데 복도는 양방향이다** — 목표 반대로 뻗어도 러너가 먼 끝에서
뿌리 쪽으로 타면 그게 곧 전진이다(실제로 전환 5회짜리 고속도로가 나왔다). 그래서 뿌리 반경 3 안에
**똬리를 틀게** 묶었고, 그 제약에서 6칸짜리는 1231번 시도에 23번만 자라고 그중 6번만 하한을
안 깨뜨렸다. **4칸이면 왕복 8칸 = 96m ≈ 10초 손해**라 벌로는 충분하다.

### 3.4 씬 빌드

`t5doorsemit.py`가 `t5doors.json` → **`t5doors.txt`**(235줄)로 내린다. 한 줄 = 한 오브젝트:

```
GRID 10 12.0 120.0 10.0 2.0 15.0          n · 피치 · 범위 · 문폭 · 두께 · 높이
DOOR DoorV_0_0 12.0 6.0 2.0 10.0 Black    이름 · cx · cz · sx · sz · 색
PAD  Pad_Z9_White 102.0 96.536 White 9    이름 · cx · cz · 색 · 구간번호
```

| 것 | 값 |
|---|---|
| 문 이름 | `DoorV_<i>_<j>` = 칸 (i,j)-(i+1,j) 사이 / `DoorH_<i>_<j>` = 칸 (i,j)-(i,j+1) 사이 |
| 문 오브젝트 | 폭 10 · 높이 15 · 두께 2 · y = 7.5 · `Rigidbody`(`DoorController` 요구) |
| 부모 | `Doors/Blue` … `Doors/White` (6색 그룹 → `ColorGateController.doorGroups`) |
| `NavMeshObstacle` | **붙이지 않는다**(§1.7) |
| 패드 | `Pads2F/Zone_1`~`Zone_9` 아래 6개씩, y는 2층 윗면(25.0) |

`t5doorsemit.py`는 격자 미리보기도 같이 찍는다 — 칸 사이 글자가 그 경계의 문 색이고
(B/P/G/Y = 고유, K = 흑, W = 백), **대문자가 의도 경로 위의 문**, `o`가 의도 경로가 지나는 칸이다.

## 6. V단계 (사용자 — 빌드 2개 환경)

**시작 시퀀스**
- 커튼이 걷힐 때 **문 색이 이미 확정돼 있는가** (게이트 `t5.map`)
- 3초 뒤 안내자만 발사되고 **러너는 그 자리에 남는가**
- 발사가 2층에 **닿는가** — 모자라면 재발사로 복구되는가 / 넘쳐 난간을 넘지 않는가
- 2층 트리거 발동 시점에 **발판이 꺼지고 barrier가 풀리는가**
- **§1.3 가 안 검증** — 구멍으로 내려가려 하면 다시 올라가는가 / 이중 가속되지 않는가
- 러너가 시작 존을 벗어날 때 **체이서 4마리**가 나오는가 (솔로 포함)

**핵심 — 새 구조에서 처음 확인하는 것**
- **문 180개 동시 존재의 부하** — 전환 1회에 60개가 움직인다(§1.4). 프레임 드랍·네트워크 튐
- **체이서가 문을 실제로 통과하는가** (레이어 매트릭스) / NavMesh를 벗어나 끼지 않는가
- **4 m/s가 체감상 맞는가** — 문 대기 중 접근 압박이 있는가, 열린 직후 따돌릴 수 있는가
- **최소 전환(12 이상)이 실전에서 몇 회로 늘어나는가** — 최소 12 기준 15~18 예상. 110초의 근거
- **안내자가 구간을 따라 이동하는 흐름이 성립하는가** — 40m ≈ 4초가 병목인가
- **2인**: 안내자 1명이 4종류(고유1·Common·흑·백)를 혼자 밟는 체감
- **솔로**: 흑백 고정 미로로 클리어 가능한가, 몇 초 걸리는가(예상 42~48초 + 회전 감속)
- 문턱에서 전환을 맞으면 러너가 튕기는가 — **사양이지만 빈도가 과한지**(§1.4 ⚠️)

**클리어·실패**
- 러너 1층 Goal + 안내자 전원 2층 Goal → 클리어
- 110초 → 실패 → 리로드 시 **러너·색 순열 재추첨**
- 러너/안내자 사망 → **즉시 실패** → 리로드
- **러너 로테이션**(§1.10) — 연속 2판에서 같은 사람이 러너가 되지 않는가

## 8. 발 헛디디기 쉬운 곳

- **`TipUI`는 String Table을 먼저 읽는다.** 코드 폴백만 고치면 화면은 하나도 안 바뀐다.
  실제로 이 함정에 빠져 "갱신했다"고 잘못 보고한 적이 있다.
- **`ColorGateController.SnapAllClosed()` → `ApplySlotMapping()` 순서.** 스냅이 "적용 완료" 표식을
  세우므로 재매핑이 뒤에 와야 한다.
- **"패드 위에 서 있는데 내 문이 안 열린다" = 사양이다**(§1.4). `OnTriggerStay` 재발동을 넣지 말 것 —
  두 안내자가 각자 패드에 서 있으면 프레임마다 색이 뒤집혀 문이 떨리고 NV가 초당 수십 회 나간다.
  **구간마다 패드가 6개씩 모여 있는 새 배치에서는 이 위험이 더 커진다** — 링 간격 4m를 지킬 것.
- **`ContactKnockback`은 대상도 속도 방향도 보지 않는다.** 러너 제외는 발판을 끄는 것으로,
  이중 가속 방지는 트리거를 나중에 켜는 것으로 푼다(§1.2).
- **`DoorController`의 닫힘 넉백은 `Player`에만 걸린다** — 체이서는 안 밀린다(코드 확인 완료).
  **러너는 밀린다**(§1.4 ⚠️).
- **`ReachZoneObjective`는 존 하나가 전원을 요구한다**(§1.8). 그대로 두 개 쓰면 둘 다 미완이다.
- **`SurviveTimeObjective`는 시간을 채우면 클리어다**(§1.8). T5와 승패가 반대다.
- **`Floor1F`를 `NavMeshSurface` 바깥으로 빼면 체이서가 안 움직인다**(§2).
- **좌표계가 또 바뀌었다**: −50~+50 → 0~100 → 0~120(피치 10 · 12×12) → **0~120(피치 12 · 10×10)**.
  **칸 중심이 5·15·25…에서 6·18·30…으로 바뀌었다** — 구 스크립트·구 문서 값을 그대로 쓰면 전부 어긋난다.
- **격자 기하가 전환 수의 하한을 정한다**(§3.2). 최소 18수 ÷ 색 사슬 길이 ≈ 전환 수라,
  2칸 사슬이 깔려 있으면 시드를 몇천 개 뽑아도 12가 안 나온다. 보정(`repair`)이 그래서 있다.
- **최소 전환은 구간 수 S를 못 넘는다**(§3.2). 의도 경로가 언제나 S짜리 길이기 때문이다.
- **오답 가지 복도는 양방향이다**(§3.3). 목표 반대로 뻗어도 먼 끝에서 뿌리로 타면 지름길이 된다 —
  뿌리 반경 안에 똬리를 틀게 묶어야 한다.
- **"없는 색 → Common"을 문 180개에 그대로 적용하면 2인에서 문의 절반이 한 번에 열린다**(§1.4 ⚠️).
  구 15문짜리 설계에서 넘어온 규칙이라 규모가 안 맞는다.
- **경로 칸 수는 홀수만 가능하다**(§3.1). 짝수를 넣으면 생성기가 조용히 실패한다.
- **`Goal`이 (96,0.6,96)에 남아 있다**(§2-4). 0~100 시절 값이라 지금 격자에서는 칸 (9,9) 위다.
- **시작 홀 스폰 두 자리에 바닥이 없다**(§2-6). `Ground`가 z=−68로 이동했고 `Floor1F`는 −1부터다.
