## A. 씬 준비 게이트 — 커튼은 조건으로 걷는다

### A.1 문제

예전엔 커튼이 **고정 시간** 뒤에 걷혔다. "A가 먼저 호출돼서 B가 호출이 안 됐는데 그대로 내보냄"이
그대로 화면에 노출됐고, 커튼을 만든 이유 자체가 무너졌다. T5 라운드 전환이 대표적이었다 —
`WaitForSecondsRealtime(coverFade)` → 텔레포트 → `WaitForSecondsRealtime(coveredHold)` → 해제.

### A.2 규칙 (확정)

> **등록된 준비 게이트가 전부 끝나야 커튼이 걷힌다. 그리고 전원이 끝나야 한다.**

```
BeginCover
  → 각 씬 컴포넌트가 RegisterGate("...")로 자기 조건 등록
  → 조건 끝나면 MarkGateReady("...")
  → 내 로컬 게이트가 전부 끝남
  → StageNetworkState가 Host에 ReportSceneReadyServerRpc(내 비트)
  → Host가 _sceneReadyMask에 비트 OR
  → 전원 비트가 켜지면 각 머신이 로컬로 마지막 게이트를 풀고 커튼을 걷는다
```

| 값 | 확정 |
|---|---|
| 타임아웃 | **5초** (`LoadingCurtain.gateTimeoutSeconds`) |
| 최소 유지 | **0.8초** (`defaultMinHoldSeconds`, 기존값 유지) |
| 페이드 | **0.35초** (`defaultFadeDuration`, 기존값 유지) |
| 재시도 | **1회** — 조용한 리로드 |
| 상한 초과 | **그냥 걷고 진행** (경고 로그) |

### A.3 등록은 **코드 자기등록**, 인스펙터 선언이 아니다

씬 인스펙터에 "기다릴 목록"을 선언하는 안은 버렸다.

> 코드에 조건을 추가하고 **씬 선언을 빠뜨리면 그 조건을 그냥 안 기다리고 조용히 통과**한다.
> 이 장치를 만든 이유가 소리 없이 무너진다. 코드 자기등록은 반대로 게이트가 안 오면
> 타임아웃 로그로 **시끄럽게** 드러난다. 조용한 실패보다 시끄러운 실패가 낫다.

**등록 레이스는 없다.** 기본 게이트(`OnPlayersReady`)는 씬 로드 + 전원 스폰 **이후**에 오고,
씬 컴포넌트의 `Start()`는 그보다 항상 먼저다. 등록은 `Start()`에서 할 것(저장소 공통 관례).

> ⚠️ **비활성으로 시작하는 오브젝트는 스스로 등록할 수 없다.** 그 조건은 **항상 활성인
> 매니저급 컴포넌트**(디렉터 등)가 대신 등록한다.

**보강:** 게이트 이름은 `const string`으로 고정(오타 방지). 타임아웃 로그에 **미완 게이트 이름**이 찍힌다.

**현재 등록되는 게이트:**

| id | 거는 곳 | 조건 |
|---|---|---|
| `players` | `LoadingCurtain` | 전원 스폰(`PlayerSpawnCoordinator.OnPlayersReady`) |
| `net.allready` | `StageNetworkState` | 전원이 자기 로컬 게이트를 끝냈다고 보고(§A.4 비트마스크) |
| `t5.map` | `T5RunnerDirector` | T5 미로 맵 선택 + 러너 발판 끄기 완료. 같은 이유로 디렉터가 대신 건다 |

### A.4 왜 NV 비트마스크인가 (ClientRpc 왕복이 아니라)

"준비됐다"는 **연속 상태**이지 일회성 이벤트가 아니다 — 우리 규약("연속 상태는 NV, 일회성은 ClientRpc")대로 NV다.

- 도착이 보장되고, 늦게 본 머신도 최종값을 읽는다
- 같은 보고가 여러 번 와도 **비트 OR이라 결과가 같다(멱등)** → 클라가 마음 놓고 0.5초마다 재시도한다
- 전원 비트가 켜지면 각 머신이 **로컬로** 걷으므로 **해제용 ClientRpc조차 필요 없다**

최대 4인이라 `int` 하나면 충분하다. 비트 i = `PlayerSpawnCoordinator` 명단을 clientId 순으로
정렬했을 때 i번째.

> **용어:** 반복해서 부르는 쪽은 **재시도(retry)**, 같은 요청이 여러 번 와도 결과가 같게 만드는
> 처리는 **멱등성(idempotency)** 또는 중복 수신 가드라고 한다. 저장소의 `_selected`·`_hasApplied`·
> `_resetPending`·`State.Idle` 래치가 전부 그 역할이다.

### A.5 막혔을 때 — 조용한 리로드 1회

**⚠️ 사망 리로드 경로를 재사용하지 않는다.** `NotifyPlayerDeath…` 경로는 `NotifyStageFailed()`로
**"STAGE FAILED" 배너를 울리고 새 시드를 배포**한다. 준비 실패로 그걸 타면 아무도 안 죽었는데
실패 배너가 뜨고 판·맵·러너가 전부 재추첨된다 — "같은 판을 다시 시도"가 아니게 된다.
그래서 `ReloadSceneSilently()`라는 전용 경로를 둔다(배너 없음, 시드 유지).

재시도 횟수는 **`NetworkSessionData.SceneReadyRetryCount`(정적)** 에 둔다 —
`StageNetworkState`는 씬 리로드마다 새로 생기므로 거기 두면 매번 0으로 초기화된다.
성공하면 0으로 되돌린다.

**상한(1회)을 넘기면 포기하고 그냥 진행한다.** 타이틀 복귀는 **폐기**했다.

### A.6 알아둘 것

- **한 명 때문에 전원이 최대 5초 기다린다.** 어긋난 화면을 막는 대가이고, 타임아웃이 곧 최악치다.
- 타임아웃 타이머는 **새 진전이 있을 때마다 다시 시작한다**(씬 로드 완료·게이트 등록). 씬 로딩이
  길었다는 이유로 타임아웃되지 않게 하기 위함이다.
- **타이틀/로비엔 `StageNetworkState`가 없다** → 거기서는 `players` 게이트만 걸리고 전원 취합은 없다.
- ⚠️ **튜토리얼 순차 합류(§6B.2)** 는 `EntryCount`가 도중에 늘어난다. 그러면 필요한 비트 수도 같이
  늘어 이미 채워진 마스크가 불완전해진다. 현재는 타임아웃 → 재시도로 흡수하는 수준이고,
  문제가 되면 "게이트 시작 시점의 명단 스냅샷"으로 고칠 것.

## B. 색 매핑 — 빈 슬롯은 Common

### B.1 규칙 (확정)

> 씬은 항상 **4인 기준**으로 만든다(Blue/Purple/Green/Yellow + 흑/백).
> 인원이 적어 **빠진 색 슬롯은 `Common`(누구나)** 으로 바꾼다.

| 인원 | 고유색 슬롯 | Common 슬롯 |
|---|---|---|
| 4인 | 4 | 0 |
| 3인 | 3 | 1 |
| 2인 | 2 | 2 |
| 1인 | 1 | 3 |

**흑/백은 고유색처럼 항상 존재하는 색**이라 치환 대상이 아니다(그대로 통과).

**⚠️ T5는 예외다 — 거기엔 Common이 없다 (2026-09-20).**
T5는 빠진 슬롯을 Common으로 풀지 않고 **벽**으로 막는다. 그리고 **러너 색도 같은 벽**이다
(러너는 1층이라 2층 패드를 밟을 수 없으니 그 색 문이 열릴 방법이 없다).
예) 3인(노·파·보) + 노랑이 러너 → 노랑(러너)·초록(미참가) 두 색 문이 **영영 안 열리고 패드도 숨는다.**

이유는 규모다. 문이 15개였을 때는 Common으로 묶여도 8개짜리 이야기였지만, **모든 변이 문인 지금은
2인에서 문의 절반(89개)이 패드 하나로 열려** 러너가 거의 걸어서 골인한다(실측 최소 전환 5회).
자세한 것은 `TStage5RunnerRedesign.md` §1.4-1.

| | 빠진 색 | 러너 색 |
|---|---|---|
| T1 / T4 | **Common**(누구나 밟는 패드 — 의도된 완화) | 해당 없음 |
| **T5** | **벽**(영영 안 열림 + 패드 숨김) | **벽** |

코드에서 이 둘을 가르는 것은 `SessionColorSlotMap.IsSlotAbsent()`다 — `Resolve()`의 전역 의미
("빠진 색 → Common")는 T1/T4가 기대고 있어 건드리지 않았다.

### B.2 왜 구 규칙(활성 색 재배정)을 버렸나

구 규칙은 빠진 색을 살아있는 색 중 하나에게 재배정했다(2인 → 2+2).

| | 구 규칙 | Common 규칙 |
|---|---|---|
| 계산 | 셔플(뽑기) → **시드 필요** | **결정적 치환** → 시드 불필요 |
| 확정 시점 | 시드 RPC 때문에 `OnPlayersReady`까지 지연 | **씬 로드 즉시** |
| 슬롯 충돌 | 두 슬롯이 같은 고유색으로 겹칠 수 있어 보정 코드 필요 | **구조적으로 불가능** |
| 판정 코드 | — | `PressurePad`/`ColorGatePad`가 이미 Common을 지원 → **신규 판정 0** |

그래서 `StagePressurePadSetup`에서 `DistributeColors` / `BuildDesignColorMap` /
`FixDoorColorCollisions`가 통째로 사라졌다.

### B.3 Pull 규약 — push 금지

**`SessionColorSlotMap`은 아무에게도 값을 밀어넣지 않는다.** 패드·문·비주얼이 각자
`Resolve(designColor)`로 당겨가고, `Version`이 바뀌면 다시 당긴다.

구 push 방식(`StagePressurePadSetup`이 씬 전역 `FindObjectsByType`으로 훑어 `SetEffectiveColor`)은
① 나중에 생기거나 늦게 켜지는 대상이 누락되고 ② 호출 순서가 곧 정합성이며
③ 1회 적용 후 래치라 실패해도 복구 경로가 없었다.

| 조회자 | 당기는 시점 |
|---|---|
| `PressurePad` | `Awake` + `Update`의 Version 비교. 색이 바뀌면 **점유도 재평가**한다 |
| `ColorGatePad` | `Awake` + `OnEnable`(맵 재활성) + `Update`의 Version 비교 |
| `ColorGateController` | `Update`의 Version 비교 → 묶음별 `effectiveColor` + 문 비주얼 |
| `StagePressurePadSetup` | `Update`의 Version 비교 → 문 비주얼(그 문의 첫 패드 색) |

### B.4 확정 시점

| | 입력 | 확정 |
|---|---|---|
| T1 / T4 | 활성 색만 | **씬 로드 즉시** (`GameSession.Apply()` → `Rebuild()`) |
| T5 | 활성 색 + 러너 | **스테이지 1회** — 러너가 정해지는 `OnPlayersReady` 직후 (라운드마다 하던 것을 2026-09-19에 1회로) |

`SessionColorSlotMap`이 정적(DDOL 성격)인데도 **"낡은 값" 문제가 없는 이유**: 여기 들어가는 것은
세션 내내 바뀌지 않는 활성 색이고, 씬별 플래그("준비됨" 같은)가 아니기 때문이다.
그런 플래그를 DDOL에 두면 안 된다는 것은 §A와 `LoadingCurtain` 주석에 따로 적혀 있다.

### B.5 ⚠️ 미완 — Common 전용 머티리얼 (T1/T4 한정)

`ColoredDoorVisual.Apply(Common)`은 매핑에 없는 색이라 **"원본 머티리얼로 복원"** 으로 떨어진다.
→ **Common 전용 무채색 머티리얼**을 만들어 문·패드 매핑에 추가할 것.

> **T5는 이 숙제에서 빠진다(2026-09-20)** — §B.1대로 Common이 아예 없어서, 벽이 된 색 문은
> 자기 색 그대로 서 있고("이 색은 이번 판에 못 연다"가 그대로 읽힌다) 패드는 숨는다.

### B.6 ⚠️ T1 난이도가 완화된다 (의도된 것 — 사용자 확정)

구 규칙의 2인 T1은 "내 색 2슬롯 + 내가 받은 남의 색 2슬롯"이라 **4슬롯이 전부 유효한 색 퍼즐**이었고,
색 분담 자체가 협동 장면이었다. 새 규칙은 "내 색 2 + 아무나 2"라 **절반이 무료**가 된다.
2026-09-18 사용자 확정 — **완화를 받아들인다.** V단계에서 T1이 너무 쉬우면 여기로 돌아올 것.

### B.7 T1/T4 vs T5 — 빠진 색 패드 처리 차이

| | 빠진 색(+ T5는 러너 색) 패드 |
|---|---|
| T1 / T4 | **Common으로 바꿔 그 자리에 남긴다.** 패드가 통로 위에 물리적으로 놓여 있어 숨기면 길과 퍼즐 구조가 바뀐다 |
| T5 | **숨긴다.** 2층 패드는 지형이 아니라 조작 도구라 없어져도 길이 안 바뀐다. 구간당 보이는 패드는 4인 5 · 3인 4 · 2인 3 · 솔로 0개 |

경로 구조가 다르기 때문에 **처리가 다르다.** (구 규칙 "2층 Common 패드 1개만"은 폐기 — 2026-09-20)

### B.8 T5 솔로 특례 — **흑·백만 열림** (2026-09-20 교체)

솔로는 본인이 러너라 **2층에 밟을 사람이 아무도 없다.** 그래서 고유 4색은 전부 벽이 되고
**흑·백 문만 동시에 열린 고정 미로**가 된다. 2층 패드는 전부 숨긴다.

> 구 특례("문 전부 Open")는 폐기했다 — 모든 변이 문인 구조에서 전부 열면 **벽이 하나도 없는
> 120×120 빈 들판**이 되어 대각선으로 18칸 달리면 끝난다(`TStage5RunnerRedesign.md` §1.6).

## C. ❌ 변형판 Picker — 폐기 (2026-09-21. 코드 파일째 삭제)

**`StageVariantPicker` · `StageVariantPickerBase`를 삭제했다.** 프로젝트 전체에서 사용처가 0이 됐다:

| 쓰던 곳 | 지금 |
|---|---|
| T5 미로 맵 7장 | **맵 1장으로 재설계** (2026-09-20, `TStage5RunnerRedesign.md` §1.1) |
| T4 격자 판 5장 | **판 1장으로 축소** (2026-09-21, `TStage4TrapRandomization.md` §2.4.1) |
| T.Boss 붕괴 트랙 | 후보가 **1장뿐**이라 뽑기가 의미 없었다 — 판을 활성 저장으로 바꾸고 Picker 제거 |
| `StageVariantRoundPicker` | 그 전에 이미 삭제(2026-09-19, T5 라운드 구조 폐기) |

**"겹쳐 두고 시드로 하나만 켠다"는 축이 이 프로젝트에서 두 번 연속 폐기됐다.** 두 번 다 이유가
같다 — 후보를 N장 유지하는 비용은 확실한데 **플레이어가 그 차이를 인지하지 못했다.**
다시 꺼내기 전에 그 두 사례를 먼저 읽을 것.

**살아남은 규약(다른 컴포넌트가 계속 쓴다):**

- **salt는 인스펙터에 손으로 넣지 않는다** — `SceneStableRegistry<T>`가 씬 계층 경로로 정렬해
  자동 배정한다. '전 인스턴스 동일 색' 버그를 낸 이력이 있어 생긴 규약이고,
  `WallLineRandomizer`·`ArrowTrap`·`DropTrap`·`WindTrap`·`TrapPlayerTracker`가 지금도 쓴다.
- **시드에서 나오는 답은 NV에 싣지 않는다** — 입력이 시드뿐이면 전 머신이 같은 답을 낸다.
  NV가 필요한 것은 *시드에서 나오지 않는 것*뿐이다(T5 러너 clientId).
- **휴지 위치를 Awake에서 굽는 컴포넌트**(`CapacityTile`)가 들어 있는 지형은 **옮기지 않는다.**
  Picker의 `anchor` 이동을 T4·T5가 둘 다 버린 이유이며, 판이 고정된 지금은 구조적으로 안전하다.
- **지형 교체는 커튼이 덮인 뒤에** — `LoadingCurtain` 게이트(§A)는 그대로 유효하다.
  T4의 `"t4.board"`가 없어진 것은 규약이 바뀌어서가 아니라 **교체 자체가 없어져서**다.
